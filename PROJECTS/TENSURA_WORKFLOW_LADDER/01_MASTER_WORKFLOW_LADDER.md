# Master Workflow Ladder
## Operational integration: the ladder must work, not merely exist
The Workflow Ladder is the project's operating system. Every participating file carries its own live navigation ladder and work order. Its header must tell the operator what this file is for, what exact work to perform, what must already be true, what evidence proves completion, where the work came from, and the exact next destination/action. A file that only lists the master ladder but has no actionable file-specific route is non-compliant.

The work order belongs inside the file description/purpose, not only in a separate index. Use PURPOSE / WORK ORDER, PREREQUISITES, REQUIRED ACTIONS, STATUS, COMPLETION EVIDENCE, PREVIOUS FILE, NEXT DESTINATION and NEXT ACTION. Update the status and next pointer as work progresses. The checkpoint is the live resume pointer; the register is the file-route index.

The mandatory source-processing engine is `13_REUSABLE_CRAFT/CHUNK_PROCESSING_AND_HANDOFF_PROTOCOL.md` (TWL-021). Read it before actual source intake. It governs the seven processing states, per-chunk extraction, boundary carryover, reconciliation, volume closure and exact handoffs. `SOURCE_CHUNK_INTEGRATION_METHOD.md` governs adaptation fidelity; the new protocol governs the mechanical reading and tracking of every chunk. Both are required.

Writing craft is not optional reference material. During planning, drafting and review, actively apply `LIGHT_NOVEL_SERIAL_NARRATIVE_METHOD.md`, `AUTHORING_PREFERENCES.md`, `CHARACTER_INTEGRITY_AND_VOICE_LOCK.md`, `CHARACTER_FORGE.md`, `LIVING_APPEARANCE_METHOD.md` and `LSM_MASTER_PROTOCOL.md` as applicable. Chapter packets must identify which craft rules are relevant; reviews must explicitly test them. Listing a method without applying it is not compliance.

## Governing rules
1. The ladder is mandatory. A later stage cannot begin until its prerequisites are verified.
2. Every participating file begins with its own live Workflow Ladder block identifying the complete sequence, exact file stage, work order inside its purpose/description, prerequisites, required actions, current status, concrete completion evidence, previous destination and exact next destination/action.
3. This master controls the sequence. A conflicting copied header is a stop condition.
4. Every stage produces an artifact or recorded verification. "I remember doing it" is not evidence.
5. Read actual source and project files, not memory or summaries where full reading is required.
6. Record blockers honestly. Never mark unread or unverified work complete.
7. All drafts are non-canon. User approval is the only route to canon promotion.
8. This is a manual ChatGPT workflow, not an agent system.

## Source-scope expansion (v1.1.0)
Stage 01 and Stage 02 now cover source Volumes 1–7, not only 6–7. Read and map in volume order (1→7); preserve each volume's independent chunk sequence. Earlier-volume source knowledge must not be projected into a character's later or earlier time-state without a chronological anchor. The 127 source-origin files are V1–5 (73 chunks), V6 (35 files), and V7 (19 files). Ten local folder/read guides are additional project navigation files, not source imports.

## Living file ladder rules
- The master defines the stage sequence; each file defines its own local route through that sequence.
- Each file header answers: why open this file, what is its work order, what must be read first, what must be done, what proves completion, and exactly where to go next.
- The description/purpose field contains the actionable work order.
- No generic next pointers. Name the exact file path and concrete next action. If waiting for user approval/decision, name it and stop.
- After a work unit, update the file status and next pointer, then synchronize checkpoint and register.
- Source-origin bodies remain unchanged after their prefatory provenance/workflow banner.

## Mandatory feedback loops
- After Stage 09: log drafting and first-review failures.
- After Stage 11: compare first review with independent audit; log escaped defects.
- After Stage 12: assess process compliance and whether the ladder enabled a bypass.
- After Stage 14: update canon ledgers only following approval.
- Stage 15 improves future execution. It never silently changes story canon.

## Stop conditions
Stop if a required file is missing, source coverage is uncertain, source and project canon conflict, knowledge state is unclear, drafts differ, workflow version mismatches, approval is absent or protected mutation lacks explicit permission.

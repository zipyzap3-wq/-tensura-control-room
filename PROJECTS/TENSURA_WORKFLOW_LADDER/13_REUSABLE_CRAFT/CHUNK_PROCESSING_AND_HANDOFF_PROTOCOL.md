# Chunk Processing and Living Handoff Protocol

## 1. What a chunk means
A chunk is a bounded source-reading unit, not a scene, chapter, or story boundary. The source may split one scene across several files or place multiple scenes in one file. Never force the adaptation to follow file boundaries. The true unit of story understanding is the complete event/scene sequence, reconstructed across adjoining chunks.

## 2. Mandatory processing states
Every source file moves through these states in order. Do not skip or combine states merely to make progress look faster.

1. **QUEUED:** listed in the source coverage matrix, with its exact path and predecessor/successor.
2. **OPENED:** exact file opened; source identity and provenance checked.
3. **READ IN FULL:** entire body inspected from first to last line/page. A partial excerpt does not qualify.
4. **EXTRACTED:** structured notes created using the extraction schema below.
5. **BOUNDARIES CHECKED:** opening and ending context compared with adjacent chunks; cut-off scenes and carryover noted.
6. **RECONCILED:** facts, event order, cast, page ranges and uncertainties reconciled against the source coverage matrix and existing ledgers.
7. **VERIFIED:** no unexplained gap remains; evidence and exact next pointer recorded.

Only VERIFIED counts as a completed source-reading unit. If a chunk is unreadable or incomplete, set BLOCKED and record the exact issue. Never silently repair source text.

## 3. Exact processing loop
For each chunk, in source order:

A. Read the volume guide and confirm the official chunk sequence.
B. Open the exact source file and verify volume, filename, source origin, page range and provenance banner.
C. Read the complete file. Do not draft, outline a chapter, or claim source knowledge from its filename or summary.
D. Extract every meaningful event and narrative beat in order. Preserve small but consequential details: jokes, reactions, demonstrations, tactical decisions, reveals, entrances/exits, objects, promises and transitions.
E. Record every named participant and their role in each beat. Separate named source characters from unnamed background figures.
F. Record character knowledge at that point in chronology. Distinguish what the reader knows, what each character knows, what they suspect, and what remains hidden.
G. Record causal links: what triggers the event, what changes, who acts, who witnesses it, and what consequence follows.
H. Compare the chunk's first and last beats with the previous and next chunk. If a scene crosses the boundary, mark it OPEN ACROSS BOUNDARY and carry its unresolved context forward.
I. Reconcile the extracted information with the source beat ledger, cast ledger, chronology, uncertainty log and coverage matrix.
J. Update the read log with actual evidence and set the state to VERIFIED only when all checks pass.
K. Update the living handoff: exact next file, exact next action, last verified beat, open scene/carryover and any blocker.

## 4. Required extraction record
Each chunk record must include:

- Source ID, volume, exact path, source-origin repository, original blob/provenance reference where available.
- Chapter/section, printed page range, actual first and last readable page/line, and any gaps.
- Ordered beat IDs and source locators.
- For each beat: event/action; participants; location; time; cause; decision/tactic; information revealed; witnesses; reaction; immediate consequence; downstream consequence.
- Dialogue function and distinctive interaction beats when relevant; do not needlessly transcribe source prose.
- Character knowledge: known / believed / suspected / unknown, with whose knowledge it is.
- Character state changes: injury, ability, possession, relationship, obligation, location, resources or emotional consequence.
- Setups, foreshadowing, promises, unresolved questions and later payoffs to investigate.
- Source fact / inference / uncertainty / proposed addition / approved divergence classification.
- Boundary notes: previous chunk handoff, scene cut, next chunk setup, unresolved continuation.
- Extraction completeness and reviewer verification.

## 5. Cross-chunk continuity and overlap
- Preserve original files unchanged. Never merge, rename, delete or rewrite source chunks to make reading easier.
- If two chunks overlap, record the overlap and compare it. Do not count duplicated text as a second event.
- If a chunk begins mid-sentence, mid-scene or mid-action, retrieve the preceding context before interpreting it.
- If a chunk ends mid-scene, do not summarize the scene as complete. Carry the active goal, opposition, participants, positions, unresolved action and last complete beat into the next chunk.
- If source page numbering skips, repeats or conflicts, record the exact discrepancy in the uncertainty log. Do not invent missing pages.
- If OCR is garbled, quote only the minimum locator needed to identify the issue, preserve the source as-is, and create a separate issue/errata record.
- If chunks contain multiple chapters or scenes, split the extraction by semantic scene/chapter boundaries while retaining the original source locator for every beat.

## 6. Read-ahead rule
After the assigned chunk, read enough of the following source to understand the current scene's continuation, immediate consequences, setup and next canonical event before fixing an adaptation endpoint. Read-ahead is context research, not permission to mark future chunks fully processed. The queue status of a future chunk remains unchanged until its own complete processing loop is finished.

## 7. Reconciliation and volume closure
At the end of each volume:
1. Reconcile all chunk records into one ordered volume chronology.
2. Verify chapter/scene order, page coverage, chunk coverage and all boundary handoffs.
3. Check that every named participant and material responsibility is represented.
4. List unresolved source questions, duplicated ranges, missing pages and OCR issues.
5. Confirm the final beat hands off correctly to the next volume or source unit.
6. Update the master coverage matrix and checkpoint with evidence.
7. Do not begin full AU chapter planning from a volume until its relevant chronology and uncertainty state are sufficiently verified.

## 8. Living ladder inside every work file
Every project-authored file must begin with its own file-specific Workflow Ladder header. The header is an active navigation card, not decoration. It must state:
- complete 00-15 ladder;
- file ID, exact path, type and primary stage;
- work order/purpose (what this file tells the operator to do);
- prerequisites and exact required actions;
- current status and concrete completion evidence;
- previous file/task;
- exact next destination and next action;
- blocker/stop conditions and approval boundary.

The next destination must be a real repository path or a clearly named user decision. A file may point back to a controlling file when that is the next valid step, but must say why. After work is completed, update the file's status and next pointer, then update the checkpoint and register. No dead-end "continue research" pointers.

Source-origin bodies remain byte-for-byte/text-for-text preserved after their provenance banner. The ladder header is a prefatory project banner and must not alter the imported source body.

## 9. Connection to writing craft
Chunk processing feeds, and does not replace, the writing methods:
- SOURCE_CHUNK_INTEGRATION_METHOD controls fidelity, beat order, cast responsibility, creative-freedom levels and anti-compression.
- LIGHT_NOVEL_SERIAL_NARRATIVE_METHOD controls scene/sequel movement, POV, causality, action clarity, chapter movement and handoff.
- AUTHORING_PREFERENCES controls dialogue/monologue/action emphasis, living character reactions, named locations, read-ahead, purposeful POV and avoidance of bland compression.
- CHARACTER_INTEGRITY_AND_VOICE_LOCK and the character forge methods control voice, motive, personality, capability and time-state.
- LSM_MASTER_PROTOCOL is the overarching scene and prose quality protocol.
These methods must be consulted during planning, applied during drafting, and explicitly checked during review. Merely listing them is not compliance.

## 10. Required handoff format
At every session end and every chunk completion, write:

- **Current stage:** exact ladder stage.
- **Last VERIFIED source file:** exact path.
- **Last verified beat:** ID and locator.
- **Current chunk state:** one of the seven processing states above.
- **Open carryover:** scene, cast, action or question crossing the boundary.
- **Evidence updated:** exact log/ledger/matrix paths.
- **Next destination:** exact next file path.
- **Next action:** one concrete action that can be performed immediately.
- **Blockers:** exact issue or NONE.

The checkpoint is the authoritative resume pointer. The register tracks file-level routes. The source read log tracks chunk states. The coverage matrix tracks completeness. These records must agree.

## 11. No false completion
Imported is not opened. Opened is not read. Read is not extracted. Extracted is not reconciled. Reconciled is not verified. A volume is not researched because its files exist. If the actual source text was not inspected, say so plainly.

## 12. Exit gate
Stage 01 source reading may close only when every required source-origin file has a VERIFIED record or an explicit, user-visible BLOCKED exception. Stage 02 chronology may close only when the beat map, cast map, event order, cross-chunk handoffs, page coverage and uncertainties have been reconciled. Only then can later story stages rely on that material.

# Conversation Compaction & Durable Handoff Protocol

## 1. Purpose
Conversation context is temporary; repository records are durable. Compaction must preserve the information needed to resume accurately while reducing repetition and obsolete detail. A compact summary is a navigation/handoff artifact, never a substitute for source files, canon, workflow instructions or evidence.

## 2. Required priority order
When space is limited, preserve information in this order:
1. User's latest request and explicit constraints.
2. Safety/approval boundaries and non-negotiable workflow rules.
3. Current project/repository/branch and authoritative file links.
4. Confirmed decisions and established facts (clearly distinguish user-approved, working/proposed, and source-verified).
5. Current stage, completed work with evidence, unfinished work and blockers.
6. Exact next action, destination file, and prerequisites.
7. Open questions/choices requiring user input.
8. Relevant style/preferences and continuity facts.
9. Older history only if it changes present decisions or prevents a known failure.

## 3. Classification labels
Every compact handoff must separate:
- **FACT / VERIFIED:** directly confirmed from source, repository read, or tool result; include evidence/path where useful.
- **USER-DIRECTED:** explicit user instruction or preference.
- **APPROVED:** explicit user approval, with scope and artifact identified.
- **WORKING / PROPOSED:** ideas or plans not yet approved as canon/final.
- **PENDING / UNKNOWN:** unresolved, unverified, inaccessible or awaiting decision.
- **BLOCKED:** prerequisite or capability prevents progress.
- **COMPLETED:** only when concrete evidence exists; name the evidence.
Never turn a proposal into a decision, a draft into canon, a copied source into verified reading, or an intention into completed work.

## 4. Compact handoff template
Use this shape when summarizing a long conversation or preparing a fresh session:

### PROJECT / TASK
- Name, repository, branch, project root; link key authority files.

### USER INTENT / RULES
- Latest request.
- Critical constraints, style, permissions and approval gates.

### AUTHORITIES
- Exact master workflow, relevant source/canon/character/decision files.
- State which file is authoritative for each subject; avoid duplicated specs.

### CONFIRMED STATE
- Decisions/facts with classification.
- Work completed and evidence (commit, file path, verification result).

### CURRENT POSITION
- Stage, status and blocker.
- What has not been done; explicitly note critical unread/unverified material.

### OPEN ITEMS
- Decisions/questions that genuinely require user input.
- Do not ask the user to repeat information already recorded.

### NEXT ACTION
- One exact next task, destination, prerequisites and expected evidence.
- Preserve ordered queues and immediate handoff pointers.

## 5. Repository-first persistence
- Store lasting project rules, decisions, research, plans, state and workflow improvements in the proper repository files; use the checkpoint for the live resume pointer and register for file routing.
- Conversation summaries should link to those records rather than copy entire documents.
- When the user asks to “add it to the workflow/repository,” identify the durable rule/artifact, create or update its proper file, and synchronize master ladder, architecture/index/register, checkpoint and changelog as relevant.
- Do not place story canon in a context summary. Canon belongs only in its designated repository location after the approval gate.
- Never claim a repository update unless the write succeeded and the edited file was fetched/verified.

## 6. Compression rules
- Remove repeated explanations, stale status, redundant prose and obsolete instructions only after confirming they are superseded.
- Keep exact names, file paths, version numbers, branch, approval state, chronology, causal links, quantitative constraints and next pointers.
- Preserve meaningful negative constraints (“must not”, “not yet”, “not approved”), not only positive goals.
- Merge duplicates only when meaning and authority are identical; keep conflicting versions visible and resolve against the authoritative file.
- Keep a short “changed since last handoff” section when useful.
- Do not compress source excerpts or character/ability specifications in place of their source files. Link the authoritative file.
- Summaries may be concise, but no omitted detail may silently change a rule, relationship, plot causal chain or capability.

## 7. Resume verification (mandatory)
At session start:
1. Read the live checkpoint and master ladder.
2. Confirm branch/repository and exact next destination.
3. Open referenced files when their contents are needed; do not rely on a summary where full reading is required.
4. Check user approval status and all stop conditions.
5. Reconcile summary claims against repository evidence; correct stale claims.
6. Resume at the stated next action, not at a guessed or more exciting task.

## 8. End-of-session handoff
Before stopping or when context is nearing its limit:
- Record the last completed action and evidence.
- Record partial work separately from completion.
- Update checkpoint with exact next file/action and blockers.
- Update session log/changelog/register only where appropriate.
- Produce a compact user-facing handoff: current state, what changed, what remains, next action and links.
- Do not make the user reconstruct the workflow from scattered chat messages.

## 9. Quality test
A handoff passes only if a new session can answer, without guessing:
- What are we doing and which repository/branch?
- Which instructions and files are authoritative?
- What has actually been completed and verified?
- What remains unverified or blocked?
- What is approved versus merely proposed?
- What is the exact next step and where?
If any answer is missing, repair the handoff before declaring compaction complete.
